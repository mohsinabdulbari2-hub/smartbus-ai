Task: Upgrade the existing bus tracking Android/iOS app into a production-ready MVP by moving all accuracy-critical and simulation logic to the backend, while strictly keeping the current UI and APK/frontend structure unchanged.
Core Principles (Mandatory)
Do NOT rebuild the frontend from scratch.
Do NOT change UI/UX or break existing APK compatibility.
Keep all frontend components, screens, map logic structure, and styling exactly as they are.
Only modify frontend where absolutely necessary (API integration, data consumption, and performance optimizations).
Move all simulation, movement, ETA, and business logic to backend for consistency and accuracy.
1. Backend Architecture (New Core)
Bus Fleet Management (600–800 buses)
Backend generates and maintains 600–800 active buses.
Each bus must:
Belong to a valid GTFS route (using routes.txt, trips.txt, stop_times.txt, shapes.txt).
Strictly follow stop sequence.
Have unique bus_id, route_id, trip_id.
Fixed realistic speed (20–35 km/h, configurable per route type).
Database fields per bus:
bus_id, route_id, trip_id, current_stop_index
current_position (lat, lon)
current_speed
direction (forward/backward)
last_updated
status (Running / At_Stop / Delayed)
Bus Movement Engine (Backend Only)
Cron/job runs every 5–8 seconds.
Move each bus along its route using stop sequence + linear interpolation between stops (no complex physics).
At the end of route → loop back to first stop (or next trip).
Handle dwell time at stops (30–90 seconds).
Frontend Role: Only fetch and render latest positions. No local simulation.
2. Core APIs (Must Be Efficient & Lightweight)
GET /buses/live
Returns only necessary fields (bus_id, lat, lon, route_id, bearing, crowd_level, eta_to_next_stop).
Support bounding box filter for viewport (lat_min, lat_max, lng_min, lng_max).
Limit: max 100 buses per request.
GET /nearby-buses
Params: user_lat, user_lng, radius_km (default 8)
Returns buses within radius. If none → nearest 20 buses sorted by distance.
GET /routes/from-to
Params: source_stop_id, destination_stop_id
Returns best route + 1–2 alternatives with:
Total ETA
Number of transfers
Crowd prediction
Recommended bus(es)
GET /stop/{stop_id}/status
Returns upcoming buses with status: Departed | At_Stop | Approaching | Upcoming
Includes live ETA.
GET /bus/{bus_id}/details
Full details + predicted ETAs for remaining stops.
3. Backend Intelligence (Lightweight Rule Engine)
ETA Calculation (Backend)
ETA_minutes = (remaining_distance_km / speed_kmh) * 60 + dwell_adjustment
Use actual GTFS distance where possible, fallback to haversine.
Update ETA for every stop on the route.
Crowd Prediction (Rule-based, No ML)
Base level by time:
Peak hours (7-10 AM, 5-9 PM) → High
Normal hours → Medium
Night (10 PM - 6 AM) → Low
Busy stops adjustment: +1 level
Return: Low | Medium | High | Very High
Stop Status Logic
At_Stop: bus within 50m of stop and speed < 5 km/h
Departed: passed current stop
Upcoming: next stops
